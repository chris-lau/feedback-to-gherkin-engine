# Feedback → Gherkin Engine

**A QLoRA fine-tune of `Llama-3.2-3B-Instruct` that compiles messy user feedback into a problem
statement, user story, and strict Gherkin acceptance criteria — with zero conversational preamble.**

[![Open In Colab](https://colab.research.google.com/assets/colab-badge.svg)](https://colab.research.google.com/github/chris-lau/feedback-to-gherkin-engine/blob/main/notebooks/train_gherkin_qlora.ipynb)
[![License: MIT](https://img.shields.io/badge/License-MIT-0a0a0a.svg)](LICENSE)

Generalist LLMs are the wrong tool for high-throughput formatting work: they prepend pleasantries,
drift out of Gherkin syntax, and cost frontier-model prices for a syntactic transformation. This
project fine-tunes a compact 3B model into a deterministic formatting compiler and ships it as a
live, side-by-side demo.

## Quickstart

### Phase 1 — dataset (runs anywhere, no GPU, no API key)

```bash
python data/generate_synthetic.py --source local --n 250 --seed 42 --out data/raw/generated.jsonl
python data/lint_dataset.py --in data/raw/generated.jsonl \
    --out-train data/train.json --out-eval data/eval.json --strict
```

The generator covers 5 domains (Enterprise Auth/SSO, Billing/Invoicing, API/Data Ingestion,
RBAC, Reporting/Analytics) with 40 friction archetypes and paraphrase pools, so every messy
input is unique while every target is schema-perfect. For teacher-API distillation instead of
the local generator:

```bash
TEACHER_API_KEY=sk-... TEACHER_BASE_URL=https://api.deepseek.com/v1 \
python data/generate_synthetic.py --source api --n 250 --out data/raw/generated.jsonl
```

The linter enforces, on every `output`: exact section order, `As a …, I want …, So that ….`,
strict `Scenario:/Given/When/Then(/And)` Gherkin lines in order, 1–2 sentence problem
statements, no conversational tokens, no markdown. It is the same code the eval suite scores
with, so training-time and eval-time compliance can never drift.

### Phase 2 — training (Google Colab, T4)

Open [`notebooks/train_gherkin_qlora.ipynb`](notebooks/train_gherkin_qlora.ipynb) in Colab,
set `HF_USERNAME`, add an `HF_TOKEN` secret, Run all. Configuration: LoRA r=16, α=16, dropout 0
on `q_proj/k_proj/v_proj/o_proj/gate_proj/up_proj/down_proj`, `adamw_8bit`, LR `2e-4`,
3 epochs — roughly 15 minutes on a free T4.

### Phase 3 — benchmark (GPU)

```bash
python eval/run_eval.py --adapter mrchrislau/feedback-to-gherkin-lora --out eval/results.json
```

Both engines get the identical system prompt with greedy decoding on the 50 held-out samples;
metrics are Gherkin compliance, preamble rate, output tokens, and generation time. Local sanity
modes that need no GPU: `python eval/run_eval.py --lint-only` and `--mock`.

### Phase 4 — serving

Heads-up: Hugging Face requires a paid plan to *create* Gradio/Docker Spaces on cpu-basic
(only Static Spaces are free for everyone). Free personal accounts can, however, host up to
**2 Gradio Spaces on ZeroGPU** — which is the best free path anyway. All three modes work
from the same `backend/app.py`, auto-detected:

- **ZeroGPU (free, durable, recommended):** create a Gradio Space with **ZeroGPU** hardware,
  push `backend/`. The app detects the `spaces` package, wraps generation in `@spaces.GPU`,
  and streams from GPU slices (~1 s outputs vs ~9 s on CPU). Set `ADAPTER_REPO` if not using
  the default. Then set `CONFIG.spaceId` in `demo/index.html` to activate the live path.
- **Colab ephemeral (free, live one-offs):** in a GPU Colab run `SHARE=1 python backend/app.py`
  (or `demo.launch(share=True)`) and paste the printed `*.gradio.live` URL into
  `CONFIG.spaceId`. The tunnel dies with the notebook runtime and Colab's terms disallow
  persistent serving — use it for screen-shares and recordings, never as a portfolio link.
- **Anywhere else:** `python backend/app.py` runs on CPU fp32; set `PRECISION=bfloat16` on a
  GPU box. Point `CONFIG.spaceId` at its public URL.

Without any of these, the demo page plays recorded outputs from the eval run (no-cost path,
already shipped).

### Phase 5 — portfolio demo

`demo/index.html` is dependency-free (fonts + `@gradio/client` from CDN) — host it anywhere or
embed it into the case-study section of your site. Scorecard numbers read live from
`eval/results.json` on the repo's raw URL; until then the table shows project targets,
explicitly labeled.

## Methodology

### How the fine-tuning works

**Why QLoRA on a 3B base.** The task is syntactic compilation, not open-ended reasoning — once
the output format is in the weights, 3B instruct-grade capacity suffices. QLoRA keeps
`Llama-3.2-3B-Instruct` frozen in 4-bit NF4 quantization and trains only adapter matrices, so
the run costs ~15 T4-minutes, the trainable artifact is a ~100 MB adapter, and inference stays
under 4 GB of memory.

**Adapter configuration.** LoRA rank 16, alpha 16, dropout 0, attached to all seven projection
matrices — attention (`q_proj/k_proj/v_proj/o_proj`) and MLP (`gate_proj/up_proj/down_proj`).
That is ~24M trainable parameters, under 1% of the base. Rank 16 suffices because the target is
a narrow formatting distribution; training the MLP projections (not just attention) is what lets
the model absorb the schema itself — section headers and keyword order — rather than only
attention patterns.

**Data and loss.** 200 linter-validated pairs across five domains. Each example is a chat whose
system prompt is byte-identical to the strings in `eval/run_eval.py` and `backend/app.py`. Loss
is computed on assistant tokens only (responses-only masking), so gradients teach emission of
the schema, not echo of the input. Every target passed the regex linter before training — the
model never sees a malformed example.

**Optimization recipe.** 3 epochs, per-device batch 2, LR 2e-4 linear schedule with 10 warmup
steps, `adamw_8bit`, 2048 max sequence length, gradient checkpointing (`"unsloth"` mode) to fit
the T4's 16 GB. LR 2e-4 is the standard QLoRA sweet spot at small rank; more epochs on a
strict-format task buy overconfidence, not generalization.

### How it is tested

1. **Held-out split, not training accuracy.** The linter splits the corpus 80/20 with a fixed
   seed, stratified per domain; the 50 evaluation samples are never seen in any epoch.
2. **Deterministic comparison.** Both engines answer the same inputs under byte-identical
   system prompts with greedy decoding (temperature 0). The base model is the same loaded
   weights with the adapter disabled via `model.disable_adapter()` — one toggle, zero
   confounds from different checkpoints or tokenizers.
3. **Metrics are code, not judgment calls.** Compliance requires all four Gherkin keywords in
   order plus the exact user-story pattern; preamble detection is a chatter-phrase regex plus
   markdown detection; token counts come from actually generated tokens. `eval/run_eval.py`
   imports the scoring functions from `data/lint_dataset.py` — the same code that validated the
   training data — so the goalposts cannot drift. The linter itself is negative-tested: preamble,
   bullets, and wrong keyword order are provably rejected.
4. **Published only when measured.** `eval/results.json` is machine-written by `run_eval.py`
   against the pushed adapter and committed as-is; the demo scorecard reads it live and shows
   explicitly-labeled targets until it exists. `--lint-only` and `--mock` modes let the whole
   eval harness be exercised CPU-only before spending GPU time.

### Measured results

50 held-out samples · greedy decoding · identical system prompt · machine-written
[`eval/results.json`](eval/results.json):

| Metric | Base | Fine-tuned | Reading |
| :--- | :--- | :--- | :--- |
| Gherkin compliance (strict schema) | 0% (0/50) | **100% (50/50)** | the headline result — target was ≥ 95% |
| Preamble rate | 0% | 0% | the shared system prompt already suppresses chatter |
| Avg output tokens | 157 | 160 | comparable — validity, not brevity, is the win |
| Avg generation time (T4) | 5.7 s | 8.6 s | adapter overhead + slightly longer outputs |

**What the numbers actually say.** The opening hypothesis — a chatty base model needing ~50%
token squeezing — did not survive contact with a prescriptive system prompt: asked for three
exact section headers, the base model is already terse. Its real failure mode is structural.
Across all 50 held-out samples it never produced a valid `Scenario:` line, and its user stories
drift from the required pattern; the fine-tune makes strict-schema emission perfect (50/50) at
comparable length — and Gherkin that parses is exactly what downstream BDD tooling needs. The
~3 s/output latency increase is adapter overhead on the T4.
