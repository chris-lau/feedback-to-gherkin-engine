02

HOW THE FINE-TUNING WORKS

a.

Why QLoRA on a 3B base

The job is syntactic compilation, not open-ended reasoning — once the output format lives in the weights, 3B instruct-grade capacity is enough. QLoRA keeps the base model frozen and quantized to 4-bit, so only tiny adapter matrices are trained.

  • Training cost: ~15 minutes on one free Colab T4 — no multi-GPU budget
  • Inference footprint stays under 4 GB of memory; the trainable artifact is a ~100 MB adapter, not a 6 GB model
unsloth · 4-bit NF4
b.

Adapter configuration

LoRA rank 16, alpha 16, dropout 0, attached to all seven projection matrices — the attention block (q/k/v/o) and the MLP block (gate/up/down). That yields roughly 24M trainable parameters: under 1% of the base model.

  • Rank 16 is sufficient because the target behavior is a narrow formatting distribution, not new world knowledge
  • Training the MLP projections (not just attention) lets the schema itself — section headers, keyword order — be absorbed, not just attention patterns
r=16 · α=16 · dropout 0
c.

Data & the loss

200 linter-validated pairs across five domains (auth/SSO, billing, ingestion, RBAC, reporting). Each example is a chat: the system prompt (byte-identical to the one used at eval and serving), the messy ticket as the user turn, the canonical schema as the assistant turn.

  • Loss is computed on assistant tokens only (responses-only masking) — gradients teach emission of the schema, not echo of the input
  • Every target passed the regex linter before training, so the model only ever sees schema-perfect examples
200 pairs · 5 domains
d.

Optimization recipe

Three epochs over 200 pairs, batch size 2, learning rate 2e-4 on a linear schedule with 10 warmup steps, 8-bit AdamW, 2048-token context. Gradient checkpointing keeps peak memory inside the T4's 16 GB.

  • LR 2e-4 is the standard QLoRA sweet spot for small ranks; more epochs on a strict-format task only buy overconfidence, so it stops at 3
  • Trainer loss is logged every 10 steps in the notebook (§5), so the curve is inspectable in the executed version
3 epochs · 2e-4 · adamw_8bit
03

HOW IT IS TESTED

a.

Held-out split, not training accuracy

The linter splits the validated corpus 80/20 with a fixed seed, stratified per domain. The 50 evaluation samples — 10 per domain — are never seen in any epoch. Training accuracy on a formatting task is meaningless; the only number that matters is behavior on unseen feedback.

50 samples · never trained on
b.

Deterministic comparison protocol

Base and fine-tuned engines answer the same 50 inputs under byte-identical system prompts with greedy decoding (temperature 0), so results are reproducible run-to-run. The base runs through the same loaded model with the adapter disabled — same weights, same tokenizer, one toggle.

greedy · temp 0
c.

Metrics are code, not judgment calls

Gherkin compliance requires all four structural keywords in the correct order plus the exact user-story pattern and section order. Preamble detection combines a chatter-phrase regex with markdown-artifact detection. Token counts come from actually generated tokens.

  • The scoring functions are the same Python that validated the training data — eval/run_eval.py imports them, so the goalposts cannot drift between training-time and eval-time
  • The linter itself was negative-tested: malformed outputs (preamble, bullets, wrong keyword order) are provably rejected
shared linter code
d.

Published only when measured

The scorecard below shows explicit project targets until the trained adapter exists. Once eval/run_eval.py runs on the adapter, it writes eval/results.json and the scorecard reads the measured numbers from this repo's raw URL — no hand-edited results.

  • The eval suite has CPU-only sanity modes (--lint-only validates ground truth; --mock exercises the scoring plumbing) so the harness is testable before any GPU time is spent
results.json · machine-written
